# Supply-Chain Security — SLSA Levels, SBOM, and Sigstore

## Definition

Software supply-chain security covers everything between a developer's keyboard and a binary running in production: source, build, dependencies, registry, deployment. The post-SolarWinds (2020) / Log4Shell (2021) / xz-utils (2024) era has produced three concrete frameworks engineers should know:

- **SLSA** (Supply-chain Levels for Software Artifacts) — a tiered maturity model for build provenance
- **SBOM** (Software Bill of Materials) — a manifest of every component in a released artifact
- **Sigstore** — keyless signing and a transparent log for verification

These compose: SLSA describes *what* you should guarantee, SBOM lists *what's in* the artifact, sigstore is *how* you sign and verify it.

## SLSA Levels (Build Track)

Canonical: https://slsa.dev/spec/v1.2/

SLSA is organized into **tracks**, each measuring one aspect of supply-chain security with its own levels. The **Build track** (the original and most widely adopted) grades build provenance L1→L3; a **Source track** grades source-control integrity (review, retention, change management). Aim for Build-track levels first.

| Level | Build platform requirements | Provenance | Typical implementation |
|---|---|---|---|
| **Build L1** | Scripted build (not manual) | Generated but unsigned, may be incomplete | `make build`, `goreleaser` |
| **Build L2** | Hosted build platform, version-controlled source | Authenticated, signed by the build platform | GitHub Actions with attestations, GitLab CI artifacts |
| **Build L3** | Build platform is hardened against tampering; build runs in ephemeral, isolated environment | Non-falsifiable, includes build-instruction integrity | Tekton Chains, GitHub Actions w/ OIDC + cosign, in-toto attestations |

There is no Build L4; deeper dependency-provenance guarantees are handled by separate tracks rather than a fourth build level. Don't aim for L3 on day one — getting to Build L2 (signed provenance attestation per build) covers the most common supply-chain attacks.

## SBOM Formats

Two formats dominate; pick one and stay consistent:

| Format | Maintainer | Strengths | When to choose |
|---|---|---|---|
| **CycloneDX** | OWASP | Compact, security-vulnerability oriented, JSON-first | Container scanning, vulnerability management |
| **SPDX** | Linux Foundation | License-tracking heritage, ISO/IEC 5962 standard, XML/JSON/YAML | License compliance, regulatory submissions |

Generation:

```bash
# Container image
syft <image> -o cyclonedx-json > sbom.cdx.json
syft <image> -o spdx-json > sbom.spdx.json

# Source repo (language-aware)
syft dir:. -o cyclonedx-json > sbom.cdx.json

# Vulnerability scan against an existing SBOM (offline)
grype sbom:sbom.cdx.json
```

SBOMs should be **generated at build time** (when you know the exact pinned dependencies) and **stored alongside the artifact**, not regenerated later. Re-scanning the same SBOM with `grype` over time catches *newly disclosed* CVEs in already-shipped artifacts.

## Sigstore — Keyless Signing

Traditional code-signing required long-lived private keys, which leak. Sigstore replaces them with short-lived certificates issued against OIDC identities (GitHub Actions, Google, GitLab, etc.) and recorded in an append-only public transparency log (Rekor).

### Sign a container image

```bash
# In a GitHub Actions workflow with id-token: write
cosign sign --yes ghcr.io/example/api:v1.2.3@sha256:abc...
```

Cosign derives the signing identity from the workflow's OIDC token, gets a short-lived cert from Fulcio, signs, and uploads the signature plus the certificate to Rekor. No long-lived keys are stored anywhere.

### Verify in deployment

```bash
cosign verify \
  --certificate-identity-regexp '^https://github.com/example/api/.*@refs/tags/.*$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/example/api:v1.2.3@sha256:abc...
```

Either embed this in a Kubernetes admission policy (Kyverno, Connaisseur, sigstore-policy-controller) to refuse unsigned images at apply time, or run it as a pre-deploy gate in CD.

### Attestations (SLSA provenance + SBOM)

`cosign attest` attaches structured signed claims to an image:

```bash
# Attach an SBOM
cosign attest --yes --predicate sbom.cdx.json --type cyclonedx \
  ghcr.io/example/api:v1.2.3@sha256:abc...

# Attach SLSA provenance (generated by the build platform)
cosign attest --yes --predicate provenance.json --type slsaprovenance \
  ghcr.io/example/api:v1.2.3@sha256:abc...
```

Verification:

```bash
# Pull and validate the attestation
cosign verify-attestation --type cyclonedx <image> | jq '.payload | @base64d | fromjson'
```

## Reference Pipeline — GitHub Actions

```yaml
name: build-and-publish
on:
  push:
    tags: ["v*"]

permissions:
  contents: read
  packages: write
  id-token: write    # required for sigstore OIDC

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: build
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/example/api:${{ github.ref_name }}
          provenance: true                  # SLSA provenance attestation
          sbom: true                        # SBOM attestation
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Sign image with cosign (keyless)
        uses: sigstore/cosign-installer@v3
      - run: |
          cosign sign --yes \
            ghcr.io/example/api@${{ steps.build.outputs.digest }}

      - name: Generate detailed SBOM with syft
        uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/example/api@${{ steps.build.outputs.digest }}
          format: cyclonedx-json
          output-file: sbom.cdx.json
          upload-artifact: true

      - name: Attach SBOM as attestation
        run: |
          cosign attest --yes \
            --predicate sbom.cdx.json --type cyclonedx \
            ghcr.io/example/api@${{ steps.build.outputs.digest }}

      - name: Vulnerability scan (gate the release)
        uses: anchore/scan-action@v3
        with:
          image: ghcr.io/example/api@${{ steps.build.outputs.digest }}
          fail-build: true
          severity-cutoff: high
```

## Defense-in-Depth at Deploy Time

Even signed, scanned images can ship a freshly disclosed CVE. Layer:

1. **Admission policy** (Kyverno / OPA Gatekeeper / sigstore-policy-controller) rejects:
   - Unsigned images
   - Images from unknown registries
   - Images without a recent (< 30d) vulnerability scan attestation
2. **Runtime CVE rescan** of registry: re-run `grype` against stored SBOMs nightly; alert on new HIGH/CRITICAL findings in actively deployed images.
3. **Dependency pinning by digest, not tag**: `image: ghcr.io/example/api:v1.2.3@sha256:abc...` — the digest is immutable.
4. **Minimal base images**: distroless or chainguard images shrink the attack surface to near zero.

## Anti-Patterns

- **Self-signed long-lived signing keys checked into a HSM**: works, but operational burden is steep; sigstore is strictly better for new builds.
- **One SBOM per release branch, regenerated on demand**: SBOMs must be generated *at build*, not later — `npm install` between two `date`s gives different graphs.
- **Trusting only the registry's "Scan" button**: registry scans (Docker Hub, GHCR) are best-effort and don't gate deploys. Always integrate scanning into CI with a hard fail.
- **Signing nothing because "we run our own registry"**: registries get compromised. The xz-utils backdoor (2024) was shipped through legitimate package channels.
- **Pinning by tag, not digest**: tags are mutable. `latest`, `v1.2.3`, and floating release tags can be overwritten.
