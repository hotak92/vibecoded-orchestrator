# Pre-shipped KG embeddings — sidecar format

**Status (v0.2.89): DATA SHIPS.** The ingest plumbing landed in v0.2.70
(`templates/scripts/sync_knowledge_graph.py`); v0.2.89 ships the data files
for the two canonical local slots:

```
templates/knowledge/.node_embeddings.qwen3_embed.json     (qwen3-embedding:0.6b)
templates/knowledge/.node_embeddings.arctic2_embed.json   (snowflake-arctic-embed2)
```

Regenerated per release by `scripts/build_shipped_kg_embeddings.py`; the
pre-tag gate runs `python scripts/build_shipped_kg_embeddings.py --verify`
(asserts every current curated node is covered in BOTH slot files with the
right chunk counts).

## Data ships ROOT-ONLY

The curated KG set is materialized ONLY into the orchestrator root's
`knowledge/` (root-only since v0.2.81 — non-root projects read the curated
nodes via the shared-KG fan-out and hold no copies). The embedding sidecars
follow the nodes: Step 4d copies them to the ROOT `knowledge/` alongside the
`.md` files, and they are deliberately NOT in the per-project allowlist
(`_PER_PROJECT_KNOWLEDGE_FILES`) — a project without curated nodes has
nothing to ingest, and ~2.9 MB per project would be pure waste. This README
itself DOES ship per-project (allowlisted) so the format stays discoverable.

## Why

A 3rd-party VCO install re-embeds the orchestrator's ~115 curated KG nodes on
first sync. On a CPU-only / slow-Ollama machine that is the slow part of the
install (the "arctic-on-CPU install hang" class). Pre-computing those vectors
and ingesting them — instead of recomputing — removes that cost.

## Format (`schema_version` 1)

One file per named-vector slot, living in `knowledge/` alongside the node
`.md` files and `.node_formats.json`:

```jsonc
{
  "schema_version": 1,
  "slot": "qwen3_embed",                 // named-vector slot these vectors fill
  "model_id": "qwen3-embedding:0.6b",    // provenance (informational)
  "dim": 1024,                           // provenance (informational)
  "nodes": {
    "<content_signature>": {             // FULL 64-hex sha256 — see "Hash
                                         //   convention" below. NOT the
                                         //   16-hex .node_formats.json hash!
      "total_chunks": 1,
      "chunks": [
        { "chunk_num": 1, "vector": [/* float, float, ... */] }
      ]
    }
  }
}
```

Multi-chunk nodes carry one `chunks[]` entry per chunk (1-indexed `chunk_num`),
and `total_chunks` must equal `len(chunks)`. Chunk layout mirrors what an
install ACTIVE on that slot's model would produce (per-model presets differ:
a node can be single-chunk in the qwen3 sidecar and multi-chunk in the
arctic2 sidecar).

Node set mirrors the consumer exactly: TAG_HIERARCHY.md / VOCABULARY.md
(sync_all_nodes EXCLUDED_FILES) and archived-class nodes (frontmatter
`status` archived/deprecated/superseded — `_is_archived_node`) ship NO
vectors, because `sync_node` never embeds them.

## Hash convention (do NOT change — and do not confuse the two sidecars)

The `nodes` keys are the node's STORAGE-LAYER content signature:
`_content_signature_excluding_updated` in `sync_knowledge_graph.py` — the
**FULL 64-hex sha256** of (frontmatter minus the `updated:` line + body).
Excluding `updated:` means a machine-written timestamp bump keeps the key
stable; ANY body/frontmatter edit changes it.

This is deliberately DISTINCT from two neighbouring hashes:

  * `.node_formats.json` (the SUMMARY sidecar) keys entries by file path and
    stores `content_hash` = `sha256(full file text)[:16]` (the
    generate-kg-summary.py convention). An embeddings sidecar keyed by that
    16-hex hash would be a silent 100 % ingest miss — the exact
    hash-scheme-mismatch class of the 2026-07-20 summary-sidecar incident.
    `scripts/build_shipped_kg_embeddings.py` therefore IMPORTS the real
    signature function from the sync script (never re-implements it), and
    `tests/test_v0289_shipped_kg_embeddings.py` parity-locks the two.
  * The retrieval-layer dedup hash (`rl_client/content_dedup.content_sha`,
    `sha1[:12]`) answers a different question and is intentionally not
    converged (v0.2.70 dedup triage).

## Ingest gate — two non-negotiable guards

`sync_node` (in `sync_knowledge_graph.py`) consults the sidecar BEFORE
computing an embedding. It ingests the shipped vector via
`collection.data.insert(vector=...)` ONLY when BOTH hold:

1. **Staleness guard.** The sidecar entry's key equals the node's CURRENT
   content signature (`_content_signature_excluding_updated`). If the node
   was edited since the vector was computed, the stale vector is never
   ingested — the embedding is recomputed.
2. **Slot-match guard.** The sidecar's `slot` equals the install's ACTIVE
   named-vector slot (`server.text_vector_slot`). A `qwen3_embed` vector is
   never written into an `arctic2_embed` install (and vice-versa). Mixing
   embedding spaces would silently corrupt cosine search — this is the
   v0.2.70 "same-active-slot, never cross-model" invariant.

Additional safety: the chunk count must match (`len(chunks)` == the chunk
count the node would produce on this install), and every vector must be a
non-empty list of finite floats. Any guard failing → fall back to computing
the embedding (pre-v0.2.89 behaviour). When no sidecar exists for the active
slot, the loader returns `None` and the gate is a pure NO-OP.

**Dual-slot merge (v0.2.89 §8.5).** With `DUAL_EMBEDDING_ENABLED` (the
default), an ACTIVE-slot hit also consults every OTHER shipped slot's sidecar
for the same signature/chunk and merges hits into the multi-slot write —
mirroring the compute path's multi-backend fan-out. A missing/stale secondary
is NEVER computed for (the "never synthesise" rule): it simply stays
unpopulated, exactly as a partial-backend compute run leaves it.

## Regeneration

```
python scripts/build_shipped_kg_embeddings.py            # both slots + self-verify
python scripts/build_shipped_kg_embeddings.py --verify   # pre-tag gate (no backend)
```

Requires local Ollama serving both models. Because knowledge is materialized
verbatim, the shipped signature matches the installed node's → vectors are
ingested without recompute. A model bump produces a new per-slot file; old
slots remain valid for installs still on that model. Caveat: a token-DENSE
node that exceeds a small model's real context window (approximation
undercount) ships a LEADING-window vector for that slot — the same result a
truncating-Ollama compute run produces; the generator prints every such node
loudly at build time.
