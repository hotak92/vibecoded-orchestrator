# Deploying the `module-catalog` edge function (L0)

This is the public-catalog endpoint that lets the launcher render its Modules
page **before** any paid module has been pulled. See
`.claude/context/plans/v0.2.33-architecture-review-2026-05-24.md` §3 for the
response-contract this implements.

## Why a separate endpoint

Up through v0.2.32 the launcher's catalog tile for `vct-rl-reranker` was
either a hardcoded placeholder (`v0.1.1`) or — if the dev had co-located the
paid module's manifest at `<install_path>/paid-modules/vct-rl-reranker/vct-module.json` —
the parsed contents of that file. Neither path works for real users:

* real users don't have the manifest on disk pre-install (it lives inside
  the private GHCR image),
* a hardcoded placeholder drifts the moment the publisher ships a new
  version.

The `module-catalog` endpoint is the supported replacement. The launcher
fetches it on Modules-tab mount, caches the result in `app_state` for 15
minutes, and re-fetches on the tab's `↻` button. Post-install, the
launcher still reads the full manifest from `~/.vct/modules/<id>/vct-module.json`
for config-tab / dispatcher / db-migration purposes — the L0 endpoint is
catalog-display + install-time-slice only.

## Prerequisites

* Supabase CLI: `npm i -g supabase` (or via Homebrew, `brew install supabase/tap/supabase`).
* Project linked in this clone:
  ```bash
  cd launcher/supabase
  supabase link --project-ref ovpdtijpdchzlxbojhsg
  ```

## One-time: create the storage bucket

The bucket name is `paid-module-catalog`. It holds one JSON object per
module — the file name is `<module_id>.json` (e.g. `vct-rl-reranker.json`).

```bash
# Create the bucket. Keep it PRIVATE — the edge function reads with the
# service-role key and serves to the anonymous caller. We don't want
# anyone to bypass the function and hit the storage URL directly because
# (a) the storage URL doesn't add the catalog envelope (schema_version +
# fetched_at), and (b) we want a single place to add caching / rate-
# limiting later.
supabase storage create-bucket paid-module-catalog --public=false

# RLS: only the 'paid-module-author' Postgres role can write. ANON role
# has NO storage access (the edge function uses service_role internally,
# so anon never touches storage). Apply the policy:
supabase storage policy create paid-module-catalog \
  --policy 'authenticated insert,update,delete' \
  --role paid-module-author
```

(If the `paid-module-author` role doesn't exist yet, create it via the
Supabase dashboard's Database → Roles UI. It's the same role we'd use
for `paid_module_releases` writes.)

## Seed the bucket with `vct-rl-reranker`

The v0.2.7 metadata lives in this repo at
`docs/v0.2.33-l0-seed-vct-rl-reranker.json` (committed alongside this
doc). Upload it:

```bash
supabase storage cp ./docs/v0.2.33-l0-seed-vct-rl-reranker.json \
  paid-module-catalog:vct-rl-reranker.json
```

Verify:

```bash
supabase storage ls paid-module-catalog
# Expected output includes "vct-rl-reranker.json" with a recent mtime.
```

## Deploy the edge function

```bash
cd launcher/supabase
supabase functions deploy module-catalog --no-verify-jwt
```

`--no-verify-jwt` is required because this is the only public endpoint
the launcher uses **before** a license JWT exists. The function does
all its own access control by reading from a private storage bucket via
service-role — no per-user identity needed.

## Smoke test the deployed endpoint

```bash
# List all modules:
curl -s 'https://ovpdtijpdchzlxbojhsg.supabase.co/functions/v1/module-catalog' \
  -H 'apikey: <anon-key>' \
  | jq .

# Fetch one module by id:
curl -s 'https://ovpdtijpdchzlxbojhsg.supabase.co/functions/v1/module-catalog?id=vct-rl-reranker' \
  -H 'apikey: <anon-key>' \
  | jq .

# Confirm 404 for unknown id:
curl -s -o /dev/null -w '%{http_code}\n' \
  'https://ovpdtijpdchzlxbojhsg.supabase.co/functions/v1/module-catalog?id=does-not-exist' \
  -H 'apikey: <anon-key>'
# Expected: 404
```

The anon key is the same one the launcher embeds for every other
public-callable function (`validate-tier`, `rl-pull-token`, etc.).

## Pointing the launcher at a non-production endpoint (dev / staging)

The launcher reads its catalog URL from the env var
`VCT_MODULE_CATALOG_URL`. Default is the production endpoint above.

For local Supabase dev:

```bash
export VCT_MODULE_CATALOG_URL='http://localhost:54321/functions/v1/module-catalog'
```

For a staging Supabase project:

```bash
export VCT_MODULE_CATALOG_URL='https://<staging-ref>.supabase.co/functions/v1/module-catalog'
```

Set the variable BEFORE launching `vct-launcher` (the launcher reads
env once at process start; restart the binary after changing).

## Publisher CI integration (future modules)

When a paid-module publisher releases a new version, their CI should:

1. Build + push the GHCR image (existing step).
2. After GHCR push succeeds, update the catalog bucket with the new
   metadata via the Supabase service-role key:

   ```bash
   supabase storage cp ./vct-module-catalog-projection.json \
     paid-module-catalog:<module_id>.json
   ```

   where `vct-module-catalog-projection.json` is a publisher-built
   projection of the full `vct-module.json` down to the L0 contract
   shape (display + install-slice + deprecation fields only).

3. If step 2 fails, the CI MUST fail loudly — a partial release
   (image pushed, catalog stale) is worse than no release. The
   launcher's 15min client cache will pick up the new entry on the
   next refresh.

A schema for the L0 projection lives at
`docs/schemas/vct-module-catalog.schema.json` (added by Agent F's
CI gate).

## Rollback

If a bad catalog entry ships, fix it by uploading a corrected JSON to
the same path — `cp` overwrites. The launcher's 15min cache means
existing users may see stale data until they restart OR until the cache
expires; document this in the rollback runbook.
