## Problem

User added SD15 — a project whose Weaviate collections had been created
by a PRE-v0.2.0 orchestrator — and add-project hit three distinct
failures:

### Bug 1 — Schema incompatibility on pre-existing collections (BLOCKING)

Two failure modes when bootstrap-collections runs against legacy state:

* **Case-only naming conflict.** Old `SD15_development` (lowercase d)
  exists; current code POSTs `SD15_Development` (capital D). Weaviate
  stores class names case-sensitively but rejects "similar" POSTs with
  HTTP 422 `class already exists: found similar class
  "SD15_development"`.

* **Multi-named-vector mismatch.** Pre-2026-04 collections were created
  with both `ollama_embed` AND `qwen3_embed` vector slots (sometimes
  legacy `snowflake_legacy` slots too). Current `sync_knowledge_graph.py`
  writes a single named vector per object. Weaviate rejects with HTTP
  422 `collection ... is configured with multiple named vectors ... but
  received a single vector`.

Result: add-project for any project with legacy state fails silently
(per-collection warnings in `CreateProjectResult.warnings` but the
collection is unusable; kg-sync then crashes on first insert).

### Bug 2 — Optimistic counter lie in kg_sync

`launcher/src-tauri/src/commands/kg_sync.rs::run_subprocess` (lines
570–584) increments `counts.kg_succeeded` on every `🔄 Syncing node:`
log line emitted by `sync_knowledge_graph.py`. Those lines log INTENT
("about to try this node"), not OUTCOME. The only authoritative count
is the terminal `📊 KG: N succeeded, M failed` summary line.

When the script crashes mid-run (e.g. 422 from Weaviate on first
insert), it never prints the summary, so the optimistic counters
persist. SD15 reported `kg_succeeded: 17, kg_failed: 0` for a run where
ZERO nodes actually committed — all 17 increments came from the
"about-to-try" log lines.

### Bug 3 — Pre-existing-content banner renders as 3 broken columns

`launcher/src/lib/components/ProjectSelector.svelte` line 557 (PR-150,
follow-up #13) had a chain of `{#if}` blocks INSIDE a `<p class="orch-row
orch-mid">` element. `.orch-row` is `display: flex; gap: 8px` (CSS
line 1036), and Svelte 5 expands each `{#if}` into a separate flex item.
The sentence rendered as 3 broken columns, with the middle column
("preserved") hidden behind the dialog's X button.

## Approach

### Bug 1 — schema-regen step in `bootstrap_collections`

Added two helpers in `vco_lib/project_init.py`:

* `_schema_incompatible(actual, target_def_fn, name) → (bool, reason)`
  inspects a Weaviate schema dict and returns whether it diverges from
  the current spec in a non-additive way. Detection rules:
    - Legacy single-vector (no `vectorConfig`) → REGEN
    - Named-vector slot set differs (missing OR extra) → REGEN
    - `indexNullState=True` required but not set → REGEN
    - Property drift alone (additive) → NOT REGEN
      (the smart-migrate's patch_props branch already handles this
      losslessly; reserve destructive regen for the unfixable cases).

* `_extract_similar_class_name(error_body) → Optional[str]` parses
  Weaviate's `class already exists: found similar class "X"` HTTP 422
  body. Handles both the unescaped form and the JSON-escaped form
  (`\"X\"`) that the REST API actually emits. Returns the actual
  server-side name so the caller can drop it.

* `_drop_and_recreate(name, definition, ...)` snapshots the collection
  (via the existing `_snapshot_collection_for_rebuild` forensics hook —
  HIGH-4, 2026-05-01) before destroying it, then `_delete_class` +
  `_create_class` with the canonical target definition.

* `_regen_reason_tag(reason) → str` maps the free-form reason string to
  a stable tag for the JSON envelope. Tags: `case-conflict`,
  `legacy-single-vector`, `multi-vector`, `index-null-state`,
  `schema-mismatch`.

`bootstrap_collections` itself was extended to:

1. After existence check returns a schema, call `_schema_incompatible`.
   If incompatible AND not dry-run, run `_drop_and_recreate` and append
   to `result["regenerated"]`. In dry-run mode, append a
   `would-regenerate` action without mutating.

2. After a fresh-create POST raises a "similar class" 422, extract the
   actual existing name, call `_drop_and_recreate(actual_name, target_def)`
   and append `{collection, reason: "case-conflict", dropped_name}` to
   `regenerated[]`.

The Rust side (`launcher/src-tauri/src/commands/projects_v2.rs::
run_bootstrap_collections`) was extended to parse `regenerated[]` from
the JSON envelope and surface each entry as a `CreateProjectResult.
warnings` line:

```
Migrated Weaviate schema for `SD15_Development` (dropped pre-existing
`SD15_development`): case-only name conflict. The collection was
recreated with the current spec; knowledge/**/*.md on disk is the
source of truth, so the subsequent kg-sync re-populates everything.
```

When multiple collections regen, each gets its own warning with a
counter (`(1/2)`, `(2/2)`). No new event plumbing or dedicated banner
state was added — the existing `warnings` channel surfaces them via
the same toast pipeline used for every other bootstrap-collections
informational line.

### Bug 2 — counter reconciliation on crash

Added a small `reconcile_optimistic_counts_on_crash` helper in
`commands/kg_sync.rs` that runs after the subprocess exits. Two new
flags track whether the terminal summary line was parsed
(`kg_summary_seen`, `docs_summary_seen`). On non-zero exit:

* If `kg_summary_seen=false`: reset `kg_succeeded = 0`, `kg_failed =
  kg_total`. The optimistic counts are a lie; surface the truth.
* If `docs_summary_seen=false`: same for docs.
* If both were seen: counts are authoritative, keep as-is.

The error message prepends a hint so the user sees
`"crashed before completing — counts reset"` instead of being confused
by a high failed count.

**Stage-aware**: if KG completed (`📊 KG: 56 succeeded, 0 failed`
printed) and Docs crashed mid-run, the KG counts stay truthful and
only Docs gets reset.

**Why kg_sync only**: kg_summary.rs uses per-invocation counters (each
subprocess call directly reports its outcome — no optimistic increment
pattern). codegraph.rs only parses `Files analyzed: N` on `exit.success()`
— failure path explicitly uses `count=0`. Both confirmed by reading; no
fix needed.

### Bug 3 — single-string sentence assembly

Replaced the chain of inline `{#if}` blocks with:

* A TypeScript helper `leftoverSummaryText(lo: ProjectLeftovers): string`
  that builds the sentence by pushing into a string array and joining
  with `', '`. Returns one string.
* A plain `<p class="orch-leftover-text">{leftoverSummaryText(leftovers)}</p>`
  (no flex layout — the new class is block-flow with manual
  `margin-left: 24px` to line up under the icon column of the title row
  above).
* The optional install-manifest hint moved to its own
  `<p class="form-hint orch-leftover-hint">` paragraph below.

Trade-off: lost the inline `<strong>preserved</strong>` emphasis. Plain
sentence is far more readable than the broken-columns rendering; the
emphasis was minor visual flavour, not load-bearing meaning.

## Decisions

### Decision A — Surface regen as warning lines, not a separate banner state

The prompt mentioned a `regenerating` banner state ("Migrating Weaviate
schema for {collection}..." with a counter). Looking at the existing
`run_bootstrap_collections` flow, bootstrap-collections is a single
blocking subprocess inside `create_project_v2` — it doesn't have a
dedicated banner today; its output is funneled into
`CreateProjectResult.warnings` and rendered as info toasts. Adding a
real `regenerating` banner state would require:

* A new Tauri event channel (`bootstrap-progress`).
* A `<BootstrapBanner>` Svelte component.
* Per-collection event emit from inside `run_bootstrap_collections`.
* Boot-time resume plumbing if the launcher restarts mid-bootstrap.

That's the full pattern v0.2.2/v0.2.3 used for kg-sync and kg-summary,
which is multi-day work. The bugs in this patch all manifest as
post-create informational notices ("we migrated schema X because it
was out-of-date"); the user wants to KNOW it happened, not watch it
progress in real time (the regen is fast — single `DELETE` + `POST`
per collection, sub-second on a healthy Weaviate). Surfacing
regenerated[] as warning lines fits the existing channel cleanly and
keeps the patch surgical.

The Python JSON envelope IS forward-compatible with the bigger banner
treatment (entries carry `collection`, `reason`, `dropped_name`,
`detail` fields — enough to drive a real banner if we promote it
later). For v0.2.4, the warning-line treatment matches user need.

### Decision B — Narrow incompatibility detection (regen only what cannot be patched)

`_schema_delta` (used by the smart-migrate `migrate_collections`
dispatcher) treats missing properties as drift. We deliberately do
NOT trigger regen on missing properties — Weaviate's
`POST /v1/schema/<class>/properties` IS mutable on 1.28.4 (verified
2026-05-01, see `_post_property`), so additive property drift fixes
in-place via the existing `patch_props` path. Regenerating for a
missing property would be destructive overkill.

The regen path is reserved for what genuinely CANNOT be patched on
the running collection: vectorConfig slot changes (immutable per
PR 422 "vector config is immutable"), indexNullState (immutable per
PR 422 "cannot be changed"), and the legacy no-vectorConfig case.
Same lossless-rebuild reasoning as `migrate_collections`'s rebuild
branch — knowledge/**/*.md is the source of truth, post-bootstrap
kg-sync re-ingests.

### Decision C — Case-conflict via POST 422 inspection, not pre-emptive listing

An alternative for the case-only conflict was: enumerate all classes
upfront via `GET /v1/schema` (already implemented as `_list_classes`),
case-insensitive-compare against each target, and pre-emptively drop
the wrong-cased variant before POSTing. That's cleaner in some ways
(no exception-driven flow) but adds a per-class round-trip on every
bootstrap. Since case-only conflicts are exceedingly rare in practice
(only affects projects from the pre-v0.2.0 era), the POST-then-recover
path keeps the happy path zero-overhead and only pays for recovery
when actually needed. `_extract_similar_class_name` is robust to both
JSON-escaped and unescaped error bodies, so the parse is reliable.

### Decision D — kg_summary.rs and codegraph.rs do NOT need the counter fix

The user prompt flagged all three task types as candidates. Reading
each:

* `commands::kg_summary.rs::run_subprocess_loop` (lines 519–614)
  doesn't have optimistic counters — each invocation of
  `generate-kg-summary.py` returns a `NodeOutcome` enum that directly
  drives `nodes_succeeded` / `nodes_failed` / `nodes_unchanged` /
  `nodes_skipped`. There's no "log line increment" pattern; each
  counter increment reflects a real subprocess outcome.

* `commands::codegraph.rs::run_build_task` (lines 1062–1106) parses
  `files_analyzed` from `parse_files_analyzed(&stdout_str)` ONLY on
  `out.status.success()`. The failure branch explicitly uses
  `files_analyzed=0`. No optimistic count.

Only `commands::kg_sync.rs` has the `🔄 Syncing node:` per-line counter
that runs ahead of actual writes. Fix scoped accordingly.

### Decision E — Plain-text sentence (no `<strong>` emphasis) for the leftover banner

The previous markup wrapped "preserved" in `<strong>`, but it got
isolated in the middle column of the 3-column rendering. Splitting
the sentence assembly into a TS helper means the output is a single
string — restoring inline `<strong>` would require `@html` plus
explicit escaping of every dynamic count, which is risky for what's
ultimately decorative emphasis. The clean plain-text sentence reads
fine ("X agents, Y skills will be preserved; hooks, scripts and the
env block will be re-installed fresh.") and aligns with the rest of
the dialog's flat tone.

## Known limitations / trade-offs

1. **Regen is destructive when the user has stored data ONLY in
   Weaviate.** The on-disk `knowledge/**/*.md` is treated as the
   source of truth. If the user's pre-v0.2.0 orchestrator wrote KG
   nodes directly to Weaviate without a corresponding `.md` file
   (extremely rare — every code path goes through the file-first
   contract), those objects are lost. The pre-drop snapshot writes
   the object count + sample UUIDs to `install.jsonl` so a forensic
   recovery is at least possible. We do NOT auto-copy via the smart
   migrate's `_copy_collection_with_vectors` here because the regen
   targets are schema-incompatible in ways that prevent named-vector
   round-trip (the whole reason we're regenerating in the first
   place).

2. **No real-time banner for the regen step itself.** The user sees
   a post-create warning toast listing what was migrated. If a regen
   takes >2s on a slow Weaviate (large legacy collection deletion),
   the launcher's progress indicator just sits on "creating project"
   for that duration. Acceptable for now; a dedicated banner state
   is documented as a follow-up in Decision A.

3. **`_extract_similar_class_name` regex is permissive but
   conservative.** It matches both unescaped (`"X"`) and JSON-escaped
   (`\"X\"`) wrappings, but it does not handle nested escaped slashes
   or single-quoted variants beyond the most common form. If Weaviate
   changes its error message wording in a future release, the regex
   will return None and the case-conflict recovery will degrade
   gracefully to a hard error (which still surfaces in
   `CreateProjectResult.warnings` as a fall-through). The user can
   then manually drop the conflicting collection.

4. **Bug 2 fix only handles the kg-sync optimistic-counter pattern.**
   kg_summary and codegraph were inspected and confirmed not to have
   the same pattern (see Decision D). If a future task type adopts
   the per-line increment pattern, the reconciliation will need to be
   propagated there.

5. **Bug 3 lost the inline `<strong>preserved</strong>` emphasis.**
   See Decision E. The visual difference is minor and the gain
   (correct sentence rendering) is large.

## Open questions

* Should the regen banner be promoted to a first-class progress event
  (per Decision A's deferred follow-up) for v0.2.5? Argues for: large
  legacy collections (~10k objects on slow disks) could take seconds
  to drop, during which the user sees no feedback. Argues against:
  rare event, post-create warning toast suffices for the common case.
  Defer pending user signal.

* Should `bootstrap_collections` retry-with-fallback if the case-only
  drop succeeds but the recreate then fails (e.g. Weaviate goes down
  between DELETE and POST)? Today: surfaces as a hard `errors[]` entry
  via the generic create-failure path. Recovery is manual. The window
  is small (sub-second), but worth flagging.

* The legacy-multi-vector path silently drops user data. Should we
  emit a more prominent deferral entry (like
  `weaviate_unreachable_at_bootstrap`) so the user explicitly
  acknowledges data loss before regen runs? Counter-argument: regen
  ALWAYS recovers from disk; "data loss" framing is misleading
  because every committed node has a corresponding .md file. Status
  quo: pre-drop snapshot in forensics + warning toast.
